# 独立 APK 加载器设计

历史设计：用户后续明确要求恢复 NPatch 原体系与默认原包名，当前设计见 [恢复 NPatch 运行体系](2026-09-23-npatch-runtime-restore.md)。

日期：2026-09-23

状态：已实现首版并通过构建、自动检查和 Android 15 / arm64 自有样例设备验收。

后续范围扩展：用户同日批准加入内置 Hook 运行时及可选原签名兼容，详见 [内置 Hook 设计](2026-09-23-embedded-hook-runtime.md)。该扩展只完成本地验证，不能继承首版的真机验收结论。

## 已确认的需求

- 基于当前 NPatch 仓库开发，在手机上选择 APK 文件或已安装应用。
- 生成可安装的外层 APK，原始基础安装包固定存放在 `assets/base.apk`。
- 外层使用不同的包名，能够与原版在同一用户空间共存。
- 点击外层图标后运行内嵌应用，不要求原版仍然安装。
- 外层目前只提供加载能力，不提供 LSP 模块注入功能。
- 管理器围绕选择、封装、导出、安装调整界面。
- 保留原应用图标（含自适应图标）、桌面名称及多语言名称；不添加“分身”等后缀。
- 本地 APK 默认保留所选文件的显示文件名；从已安装应用提取时默认导出为“应用名称.apk”。文件名与安装包名独立。
- 导出使用系统创建文档界面处理同名文件，输入原包永远不作为生成物的写入目标。
- 未来可能通过修改 SO 加载 Gadget，本阶段不实现该功能。

## 路线选择

1. 在现有 NPatch 启动链中禁用模块：改动较少，但仍携带和初始化框架，不能作为纯加载器的最终结构。
2. 复用打包工具，增加独立轻量加载模块：推荐。保留 APK 解析、Manifest 编辑、签名和管理器文件选择能力，生成物不依赖 Xposed 初始化或模块服务。
3. 引入完整应用虚拟化运行时：适用于需要模拟原包身份的更广泛兼容需求，范围明显大于当前的独立加载器，不纳入首版。

推荐路线是以新包名运行原应用代码。它不是通用虚拟机，也不承诺为原应用模拟全部系统身份。

## 安装身份与数据

外层默认包名为 `<原包名>.wrapped`，允许在生成前修改。相同源应用和相同外层包名代表同一个封装实例；生成另一实例需要另一个包名。

生成前检查包名格式，拒绝与原包相同的包名。若设备上已存在该外层包名，仅在确定属于相同生成物且签名可更新时提供升级安装；否则提示名称冲突，不卸载已有应用。

外层使用自己的签名、UID、权限授权和数据目录。它不会读取或迁移原版私有数据，登录状态及用户设置默认独立。原版卸载后，外层仍应正常启动。

系统层看到的是外层身份。代码中写死原包名、组件包名、Provider authority、数据路径或签名的应用可能不兼容。

## 生成物

```text
wrapper.apk
  AndroidManifest.xml        外层包名、规范化后的目标组件与启动入口
  classes*.dex               原 DEX 字节副本，支持原代码读取资源 APK
  classesN.dex               首个未占用位置，轻量加载模块及其必要依赖
  resources.arsc             系统解析图标、主题等所需的原资源表
  res/...                    与原资源表匹配的资源
  lib/<abi>/...              目标应用所需的原生库，按加载策略提供
  assets/base.apk            完整、未修改的原始 APK
  assets/wrapper/config.json 版本化加载配置及原包摘要
```

结构是逻辑视图。可以复用 NestedZip 链接减少重复存储，但不得改变内嵌原包字节，也不得让打包优化成为正确性前提。

外层功能仅为加载器，但仍必须携带系统需要解析的组件声明与资源。不能只用一个空 Manifest 和 assets 中的 APK 替代这些内容。

配置记录格式版本、原包名、外层包名、原 AppComponentFactory 和原包 SHA-256。原 Application 保存在规范化后的外层 Manifest 中，ABI 在运行时根据原包和进程位数选择。嵌入原包独立于签名兼容等级，首版不通过开启签名伪装来间接开启原包嵌入。

保留旧 NPatch 格式的识别和原包提取能力；新生成物使用新的路径与独立格式标识。不要对整个仓库做不区分格式的 `origin.apk` 文本替换。

## 管理器流程

1. 选择本地 APK 或已安装应用，读取其包名、版本、图标、ABI 和分包情况。
2. 将所选输入复制为本次任务的稳定快照，避免目标应用更新后打包到另一个版本。
3. 显示外层包名、应用名称、签名配置和输出位置。
4. 生成、校验并导出 APK，显示生成日志及明确的失败原因。
5. 提供安装、打开和分享结果的操作，沿用现有系统安装交互。

移除模块列表、模块选择、作用域、模块同步等产品入口。启动生成物不依赖管理器存在；管理器卸载后也要能够启动。

使用现有 Compose 风格，不新增营销页或额外外层首页。不自动卸载原版或其他应用。

## Manifest 与共存处理

改包名前，按原包名将 Application、Activity、activity-alias 及其 targetActivity、Service、Receiver、Provider 和 AppComponentFactory 等类名转换为完整类名，避免相对类名被解析到外层包名。

保留原权限请求、组件属性、Intent filter 和资源引用。外层注册新的包名；共享 UID 等与独立身份冲突的声明必须被明确处理，不能直接沿用。

Provider authority 及应用自定义权限需要独立命名，并同步修改 Manifest 内的引用。当前 `remapAuthority` 只处理等于或以原包名为前缀的 authority，不能作为完整共存支持。

Manifest 重命名不能自动修复 DEX 或 SO 中硬编码的 authority、权限名称或外部集成约定。首版不改写原包代码，也不承诺这类应用可用；对静态可识别而不能正确处理的声明，生成前报告不支持，禁止静默删除组件。

## 轻量运行时

新增独立 `wrapper-loader` 模块，不通过现有 `LSPApplication.onLoad()` 初始化 Xposed，也不打包原有模块服务或 `libnpatch.so` 来完成启动。

复用现有加载流程中已经解决的问题及必要的反射、隐藏 API 访问手段，但不得把整个框架作为实现轻量加载的默认依赖。隐藏 API 依赖仍有系统版本兼容成本，需要设备验证。

启动顺序：读取外层配置，校验并准备原包缓存，准备目标 ABI 的原生库路径，建立代码与资源一致的加载环境，再交给原应用的工厂和 Application 完成组件创建。

接管必须发生在原 Application、Provider 等目标组件实例化之前。仅在某个 Activity 中临时创建 DexClassLoader 不满足要求。

维护外层安装身份与数据目录，同时让原包代码和资源由匹配的加载环境读取。为各组件创建入口提供一致的 ClassLoader，不仅验证主 Activity。

原包缓存使用内容摘要命名，解包使用临时文件、校验和原子发布，避免崩溃后留下可被加载的半成品。多进程准备缓存必须使用文件锁或等价机制。动态加载文件在载入前按系统要求设置权限。

缓存清理不得删除其他进程正在使用的原包或 SO。加载失败记录具体阶段和原因，不能继续在错误 ClassLoader 下启动并伪装成功。

## 首版兼容范围

先实现并验收 Android 9 及以上系统上的普通单 APK，优先验证 arm64-v8a。最低系统版本声明必须与加载器要求一致；其他 ABI 仅在有对应验证后列为支持。

首版发现 split APK、必须的动态功能分包、isolatedProcess、应用 zygote 或 sharedUserId 等尚未适配情况时，在生成前明确拒绝。不能只抽取 base.apk 然后声称已完成应用封装。

分包支持是后续独立扩展：需要保存完整 APK 集合，并处理各分包代码、资源、原生库及组件合并问题。当前设计不通过未经验证的资源合并把它压成一个 APK。

签名自校验、服务端完整性认证、加固及依赖原包身份的 SDK 不在首版兼容保证中。首版不实现签名校验绕过。

## 未来 SO 处理

生成流程保持“输入快照、分析、组装、签名、验证”的清晰阶段，未来在签名前引入 SO 处理步骤。本轮不增加无实际用途的插件框架、Gadget 配置页面或占位开关。

未来若修改内嵌原包中的 SO，必须承认该原包已被修改，其原签名不能继续作为有效性保证；若使用外部运行副本，则需独立标记修改后的产物，不能把它称为原版副本。

## 验收条件

- 对自有测试 APK，输出中的 `assets/base.apk` 与输入 SHA-256 一致。
- 输出外层签名验证通过，包名不同于原版，输出不包含 Xposed 模块启动依赖。
- 原版和外层能够同时安装，点击各自图标启动各自实例。
- 删除原版及管理器后，外层能够冷启动，不发生跳转原版或要求安装内层 APK。
- 验证原 Application、相对组件类名、Activity 跳转、Provider、Service、资源及 JNI 加载。
- 验证外层与原版数据独立，以及用相同密钥更新外层后正确切换原包缓存。
- 验证缓存损坏、空间不足、无对应 ABI、包名冲突和不支持的分包输入均产生可定位的错误。
- 在 Android 9、12、14 和可用较新版本分别记录实测结果；未测试的版本不描述为已兼容。

## 实施顺序与当前状态

首先用自有简单测试应用跑通命令行打包和无框架启动；随后加入组件、资源、JNI 与共存测试；通过后再接入管理器精简流程。这样可以先验证最关键的运行机制。

实施时保留原 NPatch 管理器，新增不含模块界面的 `wrapper-manager` 和 `wrapper-cli`。它们共用 `wrapper-patch`，使用原仓库的 apkzlib、ManifestEditor 和签名资源。`-PstandaloneWrapper=true` 只加载需要的项目，避免原有 NDK/Xposed 构建依赖。

Android 10 及以上通过 AppComponentFactory 的 ClassLoader 入口加载原包；所有版本通过隐藏 API 同步 LoadedApk 的代码路径到已校验的内嵌原包，Android 9 还需更新应用 ClassLoader。资源路径仍指向外层，外层 resources.arsc 的包名改为外层包名，以支持 SDK 按当前包名调用 getIdentifier；资源 ID、资源内容和内嵌原包字节不修改。PackageManager 仍返回外层安装身份，不实现签名伪装。当前不采用 NestedZip 存储优化，复制资源保留原压缩格式。

目标应用兼容性排查后，外层额外保留原始 DEX 字节，加载器使用首个未占用的 DEX 文件名。运行时采用系统 DelegateLastClassLoader：系统类优先，其次内嵌原包，最后才委托外层引导类加载器。这样既支持原代码自读资源 APK 中的 DEX，也确保应用类实际来自内嵌原包。自有样例检查实际类加载器的代码路径，而不仅检查能否启动。

已完成管理器 Debug/Release 构建、CLI 构建、五项自动测试和 lint 检查。真实 APK 的命令行封装及签名校验通过。后续 Android 15 / arm64 设备验收已覆盖自有样例的实际启动、组件、原生库加载、共存、数据隔离和脱离管理器运行；其他系统版本及任意目标应用的兼容性仍需分别验证。产物和构建说明见仓库根目录 `WRAPPER.md`，设备结果见 `docs/testing/2026-09-23-android15-device.md`。
